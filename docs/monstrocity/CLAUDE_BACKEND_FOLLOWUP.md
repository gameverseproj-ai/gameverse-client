# Клоду: исправления после реальной интеграции Monstrocity

Дата проверки: 21 октября 2026. Работай только в be-core. Не меняй клиент. Monstrocity остаётся отдельной одиночной игрой из Worlds, `/games/monstrocity`. Существующие OpenAPI, protocol.md и продуктовые правила обязательны. Не переписывай реализацию целиком: исправь перечисленные ошибки и добавь регрессионные тесты.

Клиент подключён к реальному backend по умолчанию. Исправлены сохранение error snapshot общим interceptor, повтор транспортного запроса с тем же ключом идемпотентности, однократное обновление revision для той же активной сессии, явный takeover и disconnect через authenticated keepalive fetch. Каталог standalone-games используется настоящим экраном Worlds. Полный браузерный сценарий прошёл. Твои 39 тестов и валидация 65 ответов по схемам проходят, но следующие контролируемые проверки обнаружили ошибки.

## 1. P1: авторитетная смерть откатывается транзакцией команды

В `MonstrocityService.command()` после reconcile/settle возвращается RUN_DEAD исключением до persist. Обёртка `locked()` откатывает транзакцию. Клиент получает snapshot со смертью, а база сохраняет живой забег.

Воспроизведение на отдельной тестовой БД: создать нового anonymous игрока и забег, выставить energy=0.01 и last_seen_at на секунду назад, вызвать pause с корректными sessionId/revision. Фактически: HTTP 409 RUN_DEAD, snapshot.run.status=dead; в БД active, energy=0.01; следующий GET возвращает active. Это не ошибка отображения клиента.

Нужно сохранять авторитетные переходы времени, офлайна, смерти и завершения действий даже при отказе в новой команде. При этом недопустимая команда не должна частично менять инвентарь или бой. Например, возвращай типизированный outcome из транзакции и формируй domain error после успешного commit; отдели settlement от исполнения команды. Не используй общий noRollbackFor для всех исключений. Revision и snapshot должны соответствовать сохранённому состоянию.

Добавь тесты: смерть от расхода энергии во время pause/sync; повторный GET остаётся dead; прогресс и collected сброшены, purchased сохранены; завершение поиска/полёта снаряда во время отклонённой команды не теряется; отказ команды не оставляет её частичных эффектов.

## 2. P2: фоновые проверки не завершают disconnected-сессии

`MonstrocitySessionRepository.findSilentSince` выбирает только active/paused. После первого прохода сессия становится disconnected и больше не проверяется. Явно отключённая сессия также исключена сразу. Смерть после outside grace фиксируется только при следующем GET/resume.

Воспроизведение: новый забег вне убежища (x=3,z=5), сессия disconnected, disconnected_at и last_seen_at 140 секунд назад, outside_return_deadline 20 секунд назад. После 35 секунд работы настоящего scheduler БД всё ещё active. Следующий GET немедленно возвращает dead/disconnected.

Включи в обслуживание истёкшие disconnected-сессии живых забегов. Обеспечь ограниченные справедливые batch, отсутствие повторного обслуживания завершённых/revoked сессий и правильный отсчёт офлайн-энергии. Не списывай один интервал дважды.

Тесты: explicit disconnect → истечение grace → maintenance без GET → persisted death; silent active → первый sweep disconnect → следующий sweep death; убежище защищает от смерти и корректно готовит recovery; повторный sweep идемпотентен.

## 3. P1: конкурентный первый bootstrap даёт HTTP 500

`ensureProfile` делает SELECT FOR UPDATE, затем INSERT при отсутствии строки. Отсутствующая строка не блокируется; параллельные запросы конфликтуют по unique key. Аналогичная схема инициализации предметов требует проверки.

На трёх новых anonymous аккаунтах по четыре одновременных GET bootstrap каждый раз получены [200,500,500,500] (порядок может отличаться). Не маскируй это клиентскими повторами.

Сделай создание профиля и исходных item stacks идемпотентным: INSERT ON CONFLICT DO NOTHING, затем корректное чтение/блокировка в транзакции. Добавь конкурентный тест 4–8 первых bootstrap: все 200, один профиль, ровно три исходных стека, без удвоения предметов. Проверь bootstrap параллельно create-run.

## 4. Согласование версии баланса и траектории боя

Backend сейчас выдаёт monstrocity-v1; клиент честно использует эту версию и сохраняет прежнюю траекторию v1. В актуальном protocol.md и локальном preview уже есть monstrocity-v2: высота цели `y = 0.45 + 0.2 * u` вместо v1 `y = 0.2 + 0.55 * u`. Это делает противника визуально ближе к земле.

Добавь отдельные неизменяемые public/private конфигурации v2 и версионированную формулу engine, сделай v2 версией новых забегов. Не меняй существующую v1 задним числом: закреплённые v1-забеги продолжаются по v1. Не отдавай private balance клиенту. Сверь полную формулу с protocol.md. Клиент поддерживает mossback и twigwalker; ограничивать сервер одним монстром не нужно.

## Как воспроизвести и принять

В приложении клиента есть `scripts/monstrocity-server-audit.cjs`. Он обращается к localhost:8080, использует docker-контейнер gameverse-db и требует `MONSTROCITY_TEST_DB=monstro_codex_*`. Запускать исключительно с отдельной БД, подключённой к тестируемому серверу. Он создаёт новых тестовых пользователей и меняет только их fixtures, проверяет совпадение БД с HTTP-сервером. Существующие пользовательские базы не использовать.

```sh
MONSTROCITY_TEST_DB=monstro_codex_e2e_20261021 node scripts/monstrocity-server-audit.cjs
```

До исправления exit code 1 ожидаем. После исправления все три проверки должны проходить. JSON выводится в `/tmp/monstro-server-defects.json`. Сохранённые результаты текущего аудита — `output/monstrocity/integration/`. Встроенное ожидание 35 секунд проверяет реальный 30-секундный scheduler.

Запусти существующие MonstrocityEngineTest и MonstrocityIntegrationTest с gameverse.integration=true на отдельной PostgreSQL БД, новые регрессии, затем schema validator. Верни краткий отчёт, точные версии public config и изменённые поля API, если они понадобились. Изменения контракта сначала опиши; не вводи скрытые несовместимости. После этого Codex повторит реальный браузерный E2E.
