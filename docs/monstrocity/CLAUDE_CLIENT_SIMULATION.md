# Клоду: Monstrocity — локальная симуляция и пакетные сохранения v1

Работай только в `be-core`. Не меняй клиент. Это **новое согласованное архитектурное решение**: Monstrocity — одиночная игра, движение/бой/онлайн-энергия/поиск рассчитываются клиентом, сервер сохраняет и проверяет прогресс пакетами. Сейчас бесплатный сервер получает чрезмерное количество `/sync`. Цель — **4 фоновых запроса в минуту на игрока** при интервале 15 секунд, без ожидания HTTP при движении или броске. Не реализовывай серверный realtime tick loop.

Этот документ заменяет требования постоянной отправки input в старых protocol.md, CLAUDE_MOBILE_MOVEMENT.md и CLAUDE_SYNC_LOAD_OPTIMIZATION.md **только для нового режима**. Старые API оставь совместимыми для старых клиентов. Продуктовые правила сохраняются. Не включай capability до готовности всех новых эндпоинтов и проверок.

## Создание/возобновление

Существующие create/resume URL, auth, Idempotency-Key, takeover остаются. Для активного забега в новом режиме ответ Snapshot расширяется полем:
```typescript
simulation: {
  engineVersion: 'monstrocity-client-v1';
  state: SimulationState;
  randomState: number; // uint32
  checkpointSequence: number; // 0 при новой сессии или последнее подтвержденное значение
}
```
`SimulationState` — **ровно** экспортированный тип из local.api, не один только публичный snapshot. Включает скрытые ранее shelters (индексы), searched, spoken, nextEncounter, shots, combatEnd, hiddenFor и часы last. `receipts` всегда `{}` на wire. `state.state` должен совпадать с внешним Snapshot (без simulation). `last` — серверный timestamp в миллисекундах, начальная точка локальных часов. На resume: сначала серверная offline reconciliation, затем новый sessionId, сброс offline/offlineEnergyAt, last=serverNow, последовательность input согласована с session. Не делай новое событие смерти только в ответе без commit.

Создавай seed на сервере. PRNG точно как `SimulationRandom`: uint32 LCG `state = (1664525 * state + 1013904223) mod 2^32`, random=state/4294967296; JS использует Math.imul. Генерация encounter UUID также потребляет PRNG по алгоритму из файла. Нельзя использовать обычный random при replay. Версию алгоритма меняем вместе с engineVersion.

Клиент НЕ рассчитывает офлайн-энергию реального аккаунта: создание/resume всегда идут на сервер. После перерыва не разрешай старому sessionId продолжить игру.

## POST /api/monstrocity/runs/{id}/checkpoints

Авторизация как у прежних команд. Заголовок `Idempotency-Key` обязателен. Тело соответствует `Checkpoint` из monstrocity-checkpoint.ts:
```typescript
{
  engineVersion: 'monstrocity-client-v1',
  sessionId: string,
  sequence: number,       // baseSequence + 1
  baseSequence: number,   // последний ACK клиента
  events: SimulationEvent[],
  state: SimulationState, // предлагаемое конечное состояние, не источник истины для денег
  randomState: number,
  disconnect: boolean
}
```
Events — упорядоченный журнал. `step`: `{kind:'step',at:number,body:{sessionId,frames:[{sequence,moveX,moveZ}]}}`; `command`: `{kind:'command',at:number,name,body,key}`. `at` — локальные часы симуляции, начатые с серверного last, НЕ произвольное wall-clock время телефона. Frame loop работает локально примерно каждые 50 ms. В один запрос входят сотни мелких шагов. Не делай транзакцию/SQL запись на каждый шаг! Локальные revision меняются на каждом шаге и команде; их нельзя смешивать с sequence сохранений.

Клиент выполняет всё сразу, включая consume/sword; использование купленного предмета до ACK — предварительное. Его проверка/списание авторитетны на сервере. Успешный ответ:
```json
{"sessionId":"...","sequence":1}
```
ACK подтверждает **весь пакет и его точное конечное состояние**. Не возвращай успешный ACK, молча исправив состояние: клиент уже продолжает с него. При несовпадении — domain error, snapshot после commit reconciliation; клиент остановит локальную игру и запросит resume. Не присылай серверный устаревший snapshot на каждый успешный ACK: он откатит уже идущую локальную симуляцию.

Идемпотентность:
- Повтор того же key и тела возвращает тот же ACK без повторного списания/награды.
- Тот же key и другое тело — INVALID_REQUEST.
- baseSequence должен совпадать с последним committed sequence; sequence=base+1.
- У клиента только один запрос сохранения in flight. Во время него копится хвост событий, который попадёт в следующий пакет. Сетевые повторы сохраняют точное тело и ключ.
- В HTTP-адаптере есть один короткий transport retry; дальше клиент делает backoff 5/10/20/30 секунд. Domain errors не повторяются бесконечно.
- После 60 секунд без успешного сохранения (конфигурируемо) клиент блокирует дальнейший прогресс. Сервер независимо ограничивает допустимый временной горизонт.

## Проверка и экономика

Нельзя слепо записывать присланные purchased, best score, loot, survival days или смерть. Минимальная обязательная валидация:
1. Ownership аккаунта/забега/session, версия engine/config/map, последовательность checkpoint и непрерывность input sequence; конечные числа, размеры payload/events, лимит времени. Рекомендуемый лимит 512 KiB и 2500 событий (клиент ограничивает очередь 2500), rate limiting на пользователя. JSON может быть намного больше обычного snapshot, но запросов существенно меньше.
2. Replay событий в памяти от последнего принятого состояния эталонными правилами v1; сравнение итогового состояния/PRNG с предлагаемым checkpoint, допуск только оговорённый для float, а не количества предметов/попаданий/таймеров. Timestamp при replay берётся из at; шаги делятся на максимум 50 ms, как в эталоне. CPU replay выполняется пакетно; БД читается/пишется один раз на пакет. Для первой версии корректный replay предпочтительнее неполной проверки правдоподобия.
3. Нельзя ускорить время: сумма elapsed не превосходит серверное время с выдачи/последнего подтверждения с небольшим сетевым допуском. Нельзя задним числом прислать движение после offline-deadline. На rejected batch **никаких частичных** изменений инвентаря/боя. При этом авторитетную reconciliation времени/смерти сохраняй даже при отклонении команды.
4. Purchased — отдельный серверный ledger. Начальное количество выдаётся в seed как разрешённый остаток; локальная трата только уменьшает его согласно допустимым consume/sword. ACK транзакционно списывает фактически потраченное. Нельзя увеличить purchased через checkpoint, нельзя дважды потратить повтором. Покупки, пришедшие во время сессии, не затираются её старым snapshot: ledger дополняется отдельно, новые предметы становятся доступны клиенту при следующем resume. Не допускай параллельной траты из второй сессии.
5. Collected берутся из проверенного результата поиска. После смерти collected и знания убежищ обнуляются, purchased сохраняются с учётом реально потраченного. BestSurvivedDays/лидерборд обновляются только проверенным результатом.
6. Применение правил симулятора v1 должно быть одинаковым в клиенте и серверном replay. Если найдёшь расхождение с прежним сервером — перечисли и согласуй, не включай capability с несовместимыми правилами. Не переписывай баланс втайне от клиента.

## Жизненный цикл и offline

Для новой сессии lease должен допускать редкие сохранения и retry (например 75 секунд при maxUnsavedMs=60000), не прежние 5 секунд. Это отдельная настройка, не частота движения. Обновляй lastSeen на подтверждённом checkpoint. Не запускай тяжёлую фоновую симуляцию: вычисляй elapsed при обращении, а фоновые проверки завершения сессий делай редкими/пакетными.

`disconnect:true` на checkpoint — сохранить пакет, затем закрыть сессию и запустить офлайн-правила от сохранённого положения. Команда disconnect также может находиться в events; её эффект не должен применяться дважды. Shelter гарантирует отсутствие офлайн-смерти от энергии; при нуле выдаётся предусмотренное recovery window на resume. Вне shelter действует grace 120 секунд из конфигурации. Обычный выход из shelter в город не убивает.

На pagehide клиент отправляет тот же пакет authenticated fetch keepalive. Доставка не гарантирована браузером; размер keepalive ограничен, крупные пакеты используют обычный fetch. Если предыдущий пакет ещё in flight, клиент сохраняет его неизменным и пытается дослать хвост/закрытие последовательно. При завершении процесса может потеряться неподтверждённый хвост: никогда не доверяй локальному preview или localStorage для восстановления. Resume возвращает последний подтверждённый сервером прогресс с offline reconciliation. Не обещаем абсолютную сохранность последних 15 секунд при убийстве приложения.
