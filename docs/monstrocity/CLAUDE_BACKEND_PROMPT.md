# Задание Клоду на сервер Монстросити

Реализуй backend самостоятельной одиночной игры Monstrocity в существующем be-core. Клиент, визуальные материалы и взаимодействия делает Codex. Не меняй клиент и не связывай игру с Neon World или Jelly World: вход напрямую из Worlds в /games/monstrocity.

Приложенные файлы обязательны к прочтению:

- MONSTROCITY_DESIGN.md — утверждённые продуктовые правила.
- monstrocity/openapi.json — OpenAPI 3.1, пути /api/monstrocity, тела запросов, snapshots и ошибки.
- monstrocity/protocol.md — обязательные правила времени, последовательности, идемпотентности, симуляции и восстановления.
- monstrocity/courtyard.manifest.json — геометрия первого клиентского квартала и точки взаимодействия.
- monstrocity/bootstrap.example.json — пример; значения баланса экспериментальные, не продуктовые константы.

Не начинай с нового проекта. Изучи существующие auth/session, persistence/migrations, validation, idempotency и configuration conventions в be-core и следуй им. Не меняй теннис и другие игры ради этой реализации. Не используй клиентские userId, часы, энергию, выигрыши или флаги убежища как авторитетные.

## Что реализовать

1. Персистентные профиль, лучший результат, стеки предметов с происхождением collected/purchased, единственный живой забег на игрока, сессии, открытые убежища, обыск, диалоги, встречи и бой. После рестарта сервера восстанавливать всё, включая recovery allowance и offline anchor.
2. Версионированную полную конфигурацию. Для живого забега закрепить version. Онлайн-расход публичен; офлайн-скорость приватна. Согласованные начальные значения: фазы day240/evening120/night240/morning120 секунд, grace120 секунд, recovery60 активных секунд. Остальное берётся из внешнего баланса.
3. Все 13 операций OpenAPI с существующей bearer authentication, проверкой владения, ограничениями чисел/батчей/частоты и структурированными ошибками. Snapshot возвращать после каждой команды. Синхронизация вводов и транзакционные команды сериализованы для одной сессии.
4. Авторитетные движение по manifest препятствий, взаимодействия по расстоянию, активные часы, энергия, optional detection, encounters, поиск и 2D-бой. Нет realtime PvP. Для первой версии достаточно HTTP sync, см. протокол.
5. Серверную паузу меню/диалогов, heartbeat, явный disconnect и восстановление при недоставленном disconnect. Проверка офлайна должна срабатывать независимо от того, вернётся ли игрок; допускается reconcile при чтении плюс фоновая очистка, если поведение одинаково. Не путать активные секунды с календарным временем.
6. Атомарную смерть: сохранить рекорд, очистить collected и известные убежища, сохранить purchased, оставить результат для экрана завершения. Новый забег начинает новую выборку убежищ, с полной энергией, стартовым убежищем на карте и гарантированными едой/водой рядом.
7. Убежище защищает от офлайн-смерти, но не расхода энергии. Возврат с нулём открывает одно сохраняемое окно восстановления, не обновляемое перезагрузками или сворачиванием. В активном меню оно остановлено; повторный вход не выдаёт новые 60 секунд.
8. Идемпотентность всех команд с побочными эффектами и дедупликацию input sequences. Проверка сохранённого idempotency result выполняется раньше revision guard. Дубли меча, еды, поиска, создания забега и resume не должны менять состояние дважды.
9. Конфликт двух устройств: один владелец активной session, явный takeover, отзыв старой. Недопустимо молча сливать два независимых управления одним персонажем.

Геометрия первого квартала предоставлена в courtyard.manifest.json. Используй её и согласуй точные коллизии с monstrocity.map.ts клиента; отдельный минимальный fixture оставь только для изолированных тестов. Не считай картинку концепта геометрией. Не выдавай клиенту все выбранные скрытые убежища или seed, позволяющий их раскрыть.

Для каталогизации предложи минимальное совместимое расширение Worlds для карточки самостоятельной игры с launchRoute /games/monstrocity. Не превращай её в портал Neon World/Jelly World. Если существующий каталог не поддерживает такой тип, опиши изменение отдельно для синхронизации с клиентом.

Покупки и реклама: НЕ реализуй неподтверждённые платежи, рекламу, revive и rewards. Нужно только хранить и корректно расходовать purchased-предметы, выдаваемые доверенным серверным механизмом. Для тестов используй fixtures; публичного grantPurchased endpoint не должно быть.

## Проверка и сдача

Покрой все 12 сценариев раздела «Проверяемые сценарии» в protocol.md. Дополнительно проверь перезапуск, отрицательные/NaN/слишком большие значения, чужие идентификаторы, два конкурентных запроса расхода, переполнение sequence, несовпадение конфигурации и обрыв соединения во время паузы/боя.

Прогони существующие релевантные тесты, новые unit и integration tests с тестовой БД. Сверь фактические JSON-ответы со схемами OpenAPI, включая null-поля и коды 409. Дай краткое описание миграций, внешних параметров, команды запуска и результатов проверок. Приложи реальный bootstrap response из тестового окружения.

Если контракт требует изменения, перечисли конкретные endpoint/schema/семантику и причину до изменения интерфейса. Не вводи альтернативные названия и поля молча. Deployment, продуктивные миграции и отправка сообщений пользователям не входят в задачу.
