# Claude: лёгкий тестовый баланс Monstrocity и перезарядка

Работай только в be-core. Клиент уже блокирует новые жесты прицеливания, пока серверный `elapsedActiveMs < nextThrowActiveMs`, а также пока проигрывается бросок. После броска пустая рука опускается к сумке; новая появляется после серверной готовности. Формат API менять не нужно.

Включи отдельную версию конфигурации для удобного тестирования реального сервера:
- оба монстра: hitsToDefeat=2, approachSeconds=40, hitRadius=0.18;
- Twigwalker: motionAmplitude=0.04, motionPeriodSeconds=8, motion=zigzag, НОВОЕ поле motionStartsDay=30;
- Mossback: motion=straight, motionAmplitude=0;
- stoneCooldownSeconds=0.9 и stoneFlightSeconds=0.45 пока сохранить: проблема была в разрешённом прицеливании во время перезарядки, а не обязательно в длительности.

Эти значения уже стоят в локальном preview клиента. Примени тот же профиль к реальному backend через новую версию конфигурации и настройку gameverse.monstrocity.config-version. Не переписывай существующие версии: активные забеги привязаны к своей версии; укажи пользователю, что лёгкий профиль применяется к новым забегам. Не сбрасывай инвентарь/прогресс для миграции.

Проверь bootstrap.config и snapshot активного забега: версия и баланс должны совпадать. Проверка попадания обязана использовать тот же motion/hitRadius, что отдаёт сервер клиенту. Добавь регрессию для cooldown: отклонённый повторный throw не продлевает nextThrowActiveMs и не расходует ресурс. Ожидаемый максимальный размах Twigwalker теперь 8% ширины арены, период 8 секунд вместо размаха 44% за 3 секунды.

## Уточнение: ранние дни вообще без уклонения

Это приоритетная правка: пользователь тестирует реальный сервер и всё ещё видит старый zigzag с первого дня. Клиент намеренно рисует snapshot.combat.target, не искажает серверную цель.

Добавь необязательное целое `Monster.motionStartsDay >= 0`; отсутствие поля = 0 для совместимости прежних конфигураций. В новой тестовой версии поставь Twigwalker motionStartsDay=30. До этого порога x=0.5: никаких боковых перемещений. Начиная с survivedDays=30 включается zigzag с заданными amplitude/period. Все вычисления цели, включая проверку прилёта камня, должны учитывать тот же порог. Привяжи день/параметры к началу боя, чтобы наступление 30-го дня в середине боя не телепортировало цель.

Проверь дни 0, 29, 30, 40; x=0.5 до порога, ограниченный размах после него; пропущенное поле сохраняет старую семантику. Клиентское локальное preview уже поддерживает это поле. Расширение добавлено в OpenAPI как необязательное. HTTP-клиент продолжает доверять target из snapshot.

Для немедленного тестирования с текущим backend, пока поля нет, используй motion=straight и motionAmplitude=0 в новой тестовой версии; затем переходи на конфигурацию с порогом. Не заявляй, что новый баланс уже действует в активном забеге старой версии. Сделай безопасный способ применить тестовый баланс к следующему бою существующего тестового забега с явной миграцией версии, без потери дней или предметов, либо документируй необходимость нового забега.
