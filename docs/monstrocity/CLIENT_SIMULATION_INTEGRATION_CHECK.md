# Проверка интеграции client simulation v1

Проверено 28 ноября 2026, локально. Production не менялся, commit/push не выполнялись.

## Окружение

- Backend: рабочее дерево `/Users/greg/IdeaProjects/be-core`, `spring-boot:run`, порт 8080, capability включена только переменной процесса.
- Отдельная PostgreSQL `monstrocity-checkpoint-audit`, порт 55432, новая БД `monstrocity_audit`, миграции V1–V20. Существующая БД пользователя не затрагивалась.
- Клиент: порт 4301, proxy.conf.json → локальный backend. Существующий 4300 с remote proxy не менялся.

## Подтверждено

1. Реальный ClientMonstrocityApi → HTTP → Java replay → PostgreSQL → ACK. В успешном 61-секундном прогоне: **4 фоновых checkpoint**, **0 /sync**. Пакеты по 296–297 событий, примерно 34–35 KB. Движение, pause/unpause отправлены внутри журнала, не отдельными HTTP командами.
2. Повтор последнего checkpoint с тем же ключом возвращает тот же sequence. Выход сохраняет хвост отдельным пакетом. Resume сохранил 60 523 ms активного времени, статус active. После resume новая последовательность checkpoint начинается с 1.
3. В браузере: bootstrap, двойное нажатие на героя, город, фоновое сохранение, reload, повторный вход. До reload: Day 1, Daylight 1:35, Energy 98. После: Day 1, Daylight 1:31, Energy 98. В БД подтверждена сессия `mode=client` с ненулевым checkpoint_sequence.
4. Независимо повторён межъязыковой replay из серверного fixture: **691 событие**, elapsed 34300 ms, position (5.8, -0.12), energy 98.24, revision 691, searched=1, PRNG=1201389365. Java и текущий TS совпали. Fixture охватывает поиск и бой; полноценный бой через UI в этом прогоне не проверялся.
5. Предыдущие клиентские проверки: полный набор Monstrocity 86 тестов и последующие 17 тестов изменённых частей прошли; production build прошёл с существующими предупреждениями CSS budget.

В браузерной консоли есть отдельная ошибка Google Sign-In: origin 4301 не разрешён в Google client ID. Она не помешала анонимному входу и Monstrocity; настройку Google не меняли.

## Ограничения / не выдавать за проверенное

- Первый API-прогон завершился SESSION_EXPIRED без подтверждённых checkpoint. После добавления диагностики транспорта повторный прогон полностью прошёл. Причина первого случая не установлена; не заявляем, что найден и исправлен отдельный дефект.
- Реальный Android/iOS и Telegram Mini App не были подключены. Успешный desktop/browser тест не доказывает устранение сообщения пользователя о мобильном запуске.
- Capability на Render не включалась. Публикация backend/client и production E2E — отдельный шаг.
- Новые checkpoint-сессии используют текущие правила клиентского симулятора. Как указано в серверном отчёте, баланс отличается от legacy: в частности используется первый монстр, поиск даёт food+water. Это не ошибка wire-контракта, но перед массовым включением нужно согласовать сохранение прежнего разнообразия/баланса и обновить обе реализации синхронно.

## Углублённая проверка 28 ноября — после запроса включения без флага

- Полный backend: **240 tests, 0 failures/errors, 0 skipped**, с `-Dgameverse.integration=true` и отдельной БД monstrocity_tests. В первоначальном запуске без этого параметра интеграционные тесты были пропущены; этот результат НЕ используется для итогового заключения.
- Полный Monstrocity client: **91 SUCCESS**. Production build проходит, остаются прежние CSS budget warnings.
- Расширенный настоящий HTTP-сценарий: ходьба к pantry, поиск, найденная еда, pause/unpause, consume, победа четырьмя бросками, потеря ACK ПОСЛЕ commit и повтор идентичного тела/key, disconnect/resume. PASS, 0 /sync, максимальный промежуток итераций 64.6 ms, 49 241 ms активного прогресса.
- Отдельный реальный lifecycle-сценарий: pagehide + visibilitychange + повтор destroy; затем 80 секунд тишины сверх 75-секундного lease. Сервер ожидаемо отвергает устаревшее сохранение SESSION_EXPIRED, клиент теперь сразу делает resume в том же вызове. PASS.
- Найдены и исправлены два клиентских дефекта: повторное закрытие уже закрытой сессии; необходимость повторно нажимать resume после доменного отказа на flush старой сессии. Сетевые ошибки по-прежнему не приводят к молчаливому выбрасыванию очереди.
- Старый первый SESSION_EXPIRED был создан в `ClientMonstrocityApi.ready`, а не возвращён сервером. Воспроизведён тот же сценарий: скачок монотонных часов на 61 секунду до первого сохранения → локальный deadline → resume восстанавливает игру. Это объясняет путь ошибки, но не устанавливает причину паузы процесса в первоначальном прогоне.
- Браузер 390×844: вход/resume, джойстик, инвентарь, остановка времени в инвентаре и возврат. Screenshot output/monstrocity-mobile-audit.png. Это проверка мобильной раскладки, не эмуляция GPU/Telegram WebView физического телефона.

### Решение о выпуске

Транспорт и восстановление проверены и исправлены. Полное включение новой симуляции со старым поведением игры пока **не одобрено** по воспроизводимой причине: оба текущих движка v1 игнорируют monsterWeights и всегда выбирают первого монстра; также меняется таблица loot. Это не недостаток логов и не необходимость прятать релиз флагом. Нужен синхронный перенос публичных правил в клиент и replay. Конкретное задание: CLAUDE_RELEASE_PARITY_FIX.md. Серверный исходный код Codex не менял согласно разделению ответственности пользователя.
