# Протокол Монстросити

Контракт v0.1 для клиентской и серверной реализации. Формальная схема — `openapi.json`, пример ответа — `bootstrap.example.json`. Сервер ещё не реализован в рамках этой работы. Продуктовые правила — `../MONSTROCITY_DESIGN.md`. Числа примера, кроме согласованных длительностей суток, 120 секунд возврата и 60 секунд восстановления, являются начальными предложениями для баланса.

## Идентичность и вход

Один существующий GameVerse bearer session. Сервер извлекает владельца из токена, никогда из тела запроса. Изоляция всех runId, sessionId, targetId обязательна. Отдельная карточка на Worlds ведёт напрямую на `/games/monstrocity`; Neon World и Jelly World в цепочке входа не участвуют. Каталог Worlds должен допускать прямой маршрут для самостоятельной игры; не создавать для неё промежуточную сцену мира. Контракт каталога согласовать с существующим API, не выдавать карточку за реализованную игру до готовности клиента.

`GET /bootstrap` загружает полную конфигурацию и актуальное состояние. Он НЕ начинает активную сессию и НЕ обновляет heartbeat. При живом забеге конфигурация относится к закреплённой версии этого забега; изменения баланса применяются к следующему забегу. Версии карты, collision/navigation geometry и арта должны совпадать у клиента и сервера. Клиент не молча подменяет неизвестную версию.

Новый игрок выбирает male/female и делает POST /runs. Возвращающийся делает POST /runs/{id}/resume. Если забег умер, сначала показываем результат, затем пользователь начинает новый. Нельзя создать второй живой забег. Bootstrap при отсутствии забега возвращает run:null/session:null. Базовый профиль доступен и до первого забега.

## Владение состоянием

Сервер хранит профиль, происхождение предметов, лучший результат, забег, открытые убежища, состояние объектов поиска, активную сессию, боевую сцену, recovery allowance и версии конфигурации. Ни энергия, ни количество дней, ни приобретённые предметы не принимаются от клиента как истинные значения.

Статическая геометрия города создаётся клиентской командой и передаётся серверу как версионированный manifest: границы, препятствия, входы, допустимые позиции объектов и кандидаты убежищ. До получения manifest разрешён явно обозначенный тестовый fixture, а не предположение о будущей карте. Сервер выбирает действующие убежища для нового забега. Seed, раскрывающий все действующие убежища, в bootstrap не передаётся. Nearby показывает доступные рядом объекты; knownShelters — уже открытые. При входе в активное убежище proximity-проверка сервера открывает его и добавляет отметку, без доверия клиентскому флагу safe.

Клиент предсказывает движение и визуальные траектории локально, затем мягко согласует позицию с сервером. Координаты мира: X вправо, Z вперёд по карте, Y высота только для рендера. Боевые координаты aimX/aimY нормализованы 0..1 по игровой области, начало сверху слева. Они не зеркалятся в RTL.

## Последовательность обмена

Одна очередь запросов на активную сессию, без параллельного sync и игровых команд. Клиент собирает направления в фиксированные тики по inputTickMs, отправляет батч через syncIntervalMs; при паузе отправляет пустые heartbeat не реже установленного сервером интервала. Пример: тик 50 мс, запрос 250 мс, максимум 10 кадров. Все эти пределы приходят в config.

Sequence начинается с 1 и непрерывно растёт в пределах sessionId. Повторные уже подтверждённые кадры игнорируются. При пробеле вернуть INVALID_REQUEST с snapshot; не двигать персонажа по частично принятому батчу. Клиент удаляет кадры по lastAcceptedInputSequence. Сервер ограничивает движение elapsed server time и скоростью персонажа, проверяет препятствия. Потерянная связь не позволяет прислать ускоренную симуляцию задним числом. Клиентский timestamp не источник времени.

Активное время, энергия, поиск, движение монстров и бой продвигаются по монотонным часам сервера. Можно использовать фиксированный тик или ленивый deterministic advance при запросах; события рассчитываются в хронологическом порядке, включая окончание энергии, попадание, конец окна меча и потерю соединения. Дни = floor(activeElapsedMs / sum(phaseSeconds) / 1000). Начальная фаза day. После завершения суток начинается day следующего дня. Паузы и офлайн не прибавляют дней.

После sync клиент отправляет команду с последней expectedRevision. Любое изменение состояния увеличивает revision. Каждая команда возвращает полный snapshot. Клиент не применяет snapshot более старой revision к тому же забегу. Idempotency-Key сохраняется при сетевом повторе; при новом осмысленном действии создаётся новый UUID. Сервер сначала проверяет уже выполненный ключ, затем revision: потерянный ответ успешного запроса должен вернуть исходный результат. Один ключ с другим телом — INVALID_REQUEST. Ключи ограничены пользователем, операцией и забегом; хранить минимум весь живой забег и 24 часа после завершения. Для POST /runs — минимум 24 часа, чтобы повтор не создавал новый забег.

409 REVISION_CONFLICT возвращает snapshot; клиент согласует состояние, не повторяет расход предмета с новым ключом автоматически. Другой живой sessionId — SESSION_CONFLICT. Явный takeover отзывает старую сессию. Старые запросы больше не могут менять состояние. Синхронизацию конфликта устройств показать отдельным понятным экраном.

## Пауза и потеря связи

Map, inventory и dialogue дают настоящую серверную паузу, без расхода энергии и продвижения активных часов, включая recovery. Клиент отображает остановку сразу, подтверждает её запросом, но при отказе восстанавливает серверное состояние. Вложенные локальные окна не должны отправлять unpause, пока хотя бы одно остаётся открытым. Еду и воду разрешено использовать в паузе инвентаря. Пауза не блокирует проверку связи.

На visibility hidden или выходе из игры отправить best-effort disconnect с текущим sessionId; его доставка не гарантируется. Сервер обнаруживает отсутствие heartbeat по disconnectAfterSeconds. Без явного disconnect граница офлайна — lastSeenAt, а не момент поздней проверки. Не продолжать игровой бой на неограниченное время отсутствия. Клиент при потере связи замораживает интеракции, показывает восстановление, затем получает авторитетный snapshot через resume. Ни один локальный экран не гарантирует, что сервер ещё не зафиксировал смерть.

Вне убежища returnDeadline = disconnectAt + outsideDisconnectGraceSeconds. Просроченный возврат приводит к смерти ровно один раз. Возврат до deadline сохраняет забег по этому правилу; обычные последствия энергии остаются применимыми. Положение внутри убежища определяется последним подтверждённым состоянием. В убежище офлайн-расход ограничивает энергию снизу нулём и не убивает. Офлайн-скорость остаётся серверной настройкой и не передаётся клиенту.

Нулевое защищённое возвращение выдаёт recoveryRemainingActiveMs = 60000 по config, только если незавершённый allowance ещё не существует. Повторные resume, refresh и переключения видимости сохраняют остаток, а не создают новый. Отсчёт останавливается в меню, продолжается при выходе из убежища на поиски. При энергии >0 защита заканчивается; при остатке 0 и энергии 0 — смерть. Новый настоящий эпизод офлайн-истощения после восстановления может снова выдать allowance.

## Поиск, жители и встречи

POST search запускает поиск только в пределах interactionRadius и в допустимом состоянии. Движение прерывает поиск. Результат выдаётся один раз по завершении searchActiveSeconds; сервер выбирает содержимое из loot table и добавляет collected. Изменение revision и содержимое инвентаря приходят в snapshot. Стартовый объект гарантирует еду и воду. Конкретные вероятности, cooldown повторного обыска и состав таблиц — серверные настройки; в первой версии один объект выдаёт добычу один раз за забег.

POST talk проверяет расстояние и возвращает dialogue.textKey для локализации. Если житель раскрывает убежище, knownShelters обновляется атомарно, повтор не раскрывает новые места бесконечно: одно раскрытие на residentId за забег. Диалог ставит игру на паузу; закрытие — unpause. Торговля и задания отсутствуют.

Сервер выбирает встречи, optional-флаг и монстра по difficulty tier текущего дня. В безопасной зоне встречи не создаются. Для optional возвращается notice: время/attention, положение и признаки. Разрыв дистанции либо потеря видимости за collision obstacle в течение loseSightSeconds отменяет встречу. Неудача ведёт в combat. Обязательная встреча проходит короткую warning-фазу перед combat. Длительность warning задаётся config.encounterWarningSeconds.

## Бой

Один монстр, отдельная сцена. Сервер хранит движения цели и снаряды, проверяет cooldown, попадания, фазы и меч. Throw принимает только направление прицеливания; попадание определяется после stoneFlightSeconds по позиции цели и hitRadius. Проекция цели и правила движения должны быть общими детерминированными функциями у клиента и сервера. Monster motion параметры описаны в config; точные формулы зафиксированы ниже.

u = clamp(elapsed / approachSeconds, 0, 1). Для straight: x=.5. Для zigzag: x=.5 + amplitude*sin(2*pi*elapsed/period). Для stop-start: продвижение происходит первую половину каждого period с двойной скоростью и стоит вторую; u рассчитывается по накопленному времени движения, так что полное приближение сохраняет approachSeconds. Для configVersion monstrocity-v2: y=.45+.2*u, чтобы персонаж шёл по земле в кадре боя. Уже начатые забеги monstrocity-v1 сохраняют прежнюю траекторию y=.2+.55*u. Движение x/y ограничено 0..1. Круг попадания радиуса hitRadius; снаряд на время броска фиксирует выбранную точку aim. При времени разрешения попадания дистанция до target <= hitRadius означает попадание. Это предложенная техническая модель первой версии, допускающая последующую смену только с новой configVersion.

После approachSeconds начинается sword-window на swordWindowSeconds. Камнями всё ещё можно победить до конца окна. Меч доступен только в этом окне, при наличии запаса; списывается collected раньше purchased, ровно одна штука, и бой становится won. Двойной тап распознаёт клиент, сервер принимает одно действие sword. Истечение окна без победы — lost и смерть. Для одновременных событий: уже запущенное попадание с timestamp <= deadline обрабатывается перед истечением окна; новые команды, полученные после deadline, не принимаются.

В won персонаж возвращается к исследованию на подтверждённой позиции после короткого отображения результата; длительность задаётся config.combatResultHoldSeconds; сервер не требует от клиента сообщения о победе. В течение победной фазы новая встреча не создаётся. В lost результат сохраняется до создания нового забега.

## Смерть, покупки и ограничения

Смерть — атомарная транзакция: сохранить best=max(best,survivedDays), выставить dead/deathReason, убрать collected из всех стеков и все знания об убежищах. Purchased остаётся в профиле. Потраченные purchased не возвращаются. Новый забег выбирает убежища заново, полную энергию и новое расположение старта, раскрывает стартовое убежище и размещает гарантированные припасы рядом.

Нет эндпоинта для клиентского добавления купленных предметов. Будущая покупка должна подтверждаться существующей проверенной серверной системой оплаты. На текущем этапе только места монетизации в дизайне: перед новым забегом, нехватка припасов, экран результата. Не внедрять возрождение, рекламу или награды, пока правила не утверждены.

## Проверяемые сценарии

1. Создать забег, повторить тот же ключ после потери ответа: один забег и один запас.
2. Пройти 720 секунд активной игры с паузой посередине: ровно один день; пауза/офлайн не добавляют дни.
3. Вернуться вне убежища до/после 120 секунд; повтор resume не меняет итог смерти.
4. Вернуться в убежище с нулём; потратить 20 активных секунд, свернуть, вернуться: осталось 40, а не 60.
5. Открыть карту на восстановлении: остаток не уменьшается, но потеря heartbeat всё равно переводит в офлайн.
6. Поиск завершён, ответ потерян: повтор не выдаёт второй набор.
7. Один collected и один purchased меч: первый бой тратит collected. Смерть сохраняет только оставшиеся purchased.
8. Нельзя подделать shelterId, energy, day, win, hit или purchase через тело запроса.
9. Старый sessionId после takeover не двигает персонажа; старый snapshot не откатывает клиент.
10. После смерти карта улиц остаётся, отметок убежищ нет; новый забег имеет свой выбор убежищ.
11. Пауза при открытом инвентаре позволяет использовать еду; закрытие не сбрасывает фазы боя.
12. При пропаже интернета из 2D-боя не проигрывать локально и не расходовать предметы без подтверждения; после resume восстановить серверную фазу.
